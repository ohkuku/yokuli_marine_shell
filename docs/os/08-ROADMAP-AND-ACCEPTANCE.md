# OS 交付顺序与验收门槛

不要用更多页面换取“像 OS”的感觉。每个阶段交付明确的能力和证据，先跑通设备生命周期，再扩大应用生态。

| 阶段 | 用户能得到什么 | 必须看到的证据 | 当前 |
| --- | --- | --- | --- |
| R0 产品集成 | AOSP 设备开机后使用 Yokuli 桌面，原航海体验可运行 | 固定产品配置、HOME APK、Linux 完整构建、Cuttlefish 开机及 HOME 解析 | 本轮完成配置与 APK；整机构建/启动待构建机 |
| R1 独立航海运行时 | 关闭/崩溃 Shell 不终止数据、记录与值守；恢复状态可解释 | 服务拥有配置与数据，断连/崩溃/重启/解锁实测，失联不冒充安全值守 | 设计完成，尚未实施 |

## 下一步真正应该写的代码

1. 先用 Linux 构建机把 R0 镜像编译、启动；验证上游 SystemUI 在 Launcher3 被替代后，原生任务切换/手势回退的实际行为。必要时先保留三键系统导航作为救援，不修改安全服务来掩盖问题。
2. 把运行时从 `MainViewModel` 的界面组合根迁出，保留既有 `VesselDataHub`、来源策略、锚警/航程逻辑。先一个明确所有者的服务进程，不急着把每个业务模块拆成独立 APK。
3. 实施持久恢复日志与明确的 `恢复待确认` 状态，再实现受权限保护的进程间读数订阅。先迁驾驶台一个消费者，跑通断线重连与时间语义，再迁地图、值守与日志。
4. 在 SystemUI/系统扩展的正确层处理全系统通知和任务。不能让 Shell 的内部应用栈伪装成 ActivityTaskManager；不能通过 root/shell 命令常态控制系统。
5. 指定第一台可维护设备，完成传感器、后台、电池、音频和离线海图长时场景；随后再谈可分发 ROM 与 OTA。

## 每层发布前共同检查

- **诚实状态**：来源时间、连接状态和业务值守状态分开；没有读数就没有虚构图形；崩溃恢复不直接标成正在保护。
- **单一所有者**：GPS、来源选择、航行、锚警与分享都只有一份配置；通知中心只发命令并订阅结果。
- **用户故事**：HOME 回桌面，Back 回当前访问来源，任务切换恢复访问；系统开场不重播于同页通知。
- **可恢复性**：异常后可以进入设置、查看状态与导出资料；升级不能清空用户文件夹权限而不解释。
- **证据与边界**：在文档中分别记录实现、编译、启动、机型、海上实测；不以某一层通过代替其它层。

研发继续沿两个分支推进：应用体验改动先在 `codex/yokuli-os-rebuild` 完成；ROM 分支选择性合入稳定业务修改，并维护平台差异。不要为了移植 ROM 把已可用的手机应用变成必须有特权才能启动的软件。
